# Станция сборки ФБО с проверкой кодов маркировки

Монолитное приложение для участка сборки ФБО: кладовщик выбирает печатную форму «Расходный ордер на товары»
из общей сетевой папки (её сохраняют из привычного экрана 1С), сканирует коды маркировки, программа сверяет
товар и количество с ордером, проверяет код в «Честном ЗНАКе», а по завершении сохраняет рядом файл
«КИЗ - …xlsx», помечает исходник префиксом «СОБРАН - » и отправляет отбивку в Битрикс24.

Стек: C# / .NET 8 (ASP.NET Core Minimal API + SignalR), SQLite, HTML/JS + Bootstrap.
Результат сборки — **один исполняемый файл** `MarkCheck.exe` (вёрстка и библиотеки встроены внутрь).

## Сборка

```cmd
dotnet publish -c Release -r win-x64 -o publish
```

Получится `publish\MarkCheck.exe` (~50 МБ, .NET на машине не нужен).
Рядом с exe при первом запуске создаётся каталог `data\` с базой `markcheck.db`.

## Запуск

1. Запустить `MarkCheck.exe` (окно консоли оставить открытым).
2. Открыть в браузере `http://localhost:5080`.
3. Раздел «Администрирование»: выбрать COM-порт сканера и его скорость, вставить
   токен True API «Честного ЗНАКа», указать ИНН организации. Сохранить.
4. Раздел «Проверка»: загрузить `.xlsx` расходного ордера → сканировать товар.

Адрес/порт меняется в «Администрировании» (`http_url`), например `http://0.0.0.0:8080`
для доступа с других ПК в сети. Изменение применяется после перезапуска.

## Логика проверки кода

1. Сканер отдаёт строку в COM-порт → `ScannerService` → обработчик; результат уходит в браузер через SignalR.
2. Разбор GS1 DataMatrix: GTIN (AI 01) и серийный номер (AI 21), КИ `01<GTIN>21<Serial>`.
3. Контроль дублей: в текущем ордере → «дубликат»; в другом ордере → «уже отгружен».
4. **GTIN → база ШК → строка ордера.** По GTIN находятся позиции базы ШК (номенклатура + характеристика).
   Один GTIN может принадлежать нескольким номенклатурам (дубли в 1С) — берётся та, что есть в открытом ордере.
   Если позиция разбита на несколько строк (разные серии) — строки заполняются по очереди.
   Ручного сопоставления больше нет: ошибки «Штрихкода нет в базе ШК» и «Товара нет в ордере» — отложить товар.
5. Проверка в «Честном ЗНАКе» (для строк с признаком `[М]`).
6. Контроль количества по строке ордера.
7. «Завершить сборку» → окно «Сколько получилось коробов?» → закрытие ордера, отчёты CSV, файл КИЗ,
   префикс «СОБРАН - », отбивка в Битрикс24. Ошибки файловых операций и Битрикса не прерывают завершение —
   показываются в итоговом окне и сохраняются в `Orders.FinishInfo`.

## Восстановление после сбоя

Ордер и все сканирования пишутся в SQLite сразу. После перезагрузки браузера или ПК
активный ордер и уже проверенные коды подтягиваются автоматически (`GET /api/state`).

## API (кратко)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/state` | активный ордер, строки (со статусом сопоставления), сканирования |
| GET | `/api/files?all=` | печатные формы в общей папке (рекурсивно; `all=true` — включая «СОБРАН - ») |
| POST | `/api/orders/open` | открыть файл из общей папки `{path, force}` |
| POST | `/api/orders/upload` | загрузить .xlsx вручную (без файла КИЗ и отбивки) |
| POST | `/api/orders/{id}/finish` | завершить сборку `{boxes}`: КИЗ, «СОБРАН - », Битрикс24 |
| POST | `/api/orders/{id}/close` | прервать (закрыть без файловых операций) |
| GET | `/api/orders/{id}/codes`, `/csv`, `/csv-full` | коды и отчёты |
| POST | `/api/scan` | проверка кода (ручной ввод) |
| POST | `/api/scans/{id}/setaside`, DELETE `/api/scans/{id}` | отложить / удалить запись |
| GET | `/api/barcodes?q=` | просмотр базы ШК |
| POST | `/api/barcodes/import`, `/api/barcodes/sync` | загрузка отчёта по ШК вручную / из папки |
| GET | `/api/journal`, `/api/journal/{id}` | журнал |
| GET/POST | `/api/settings` | настройки; `POST /api/cz/test`, `POST /api/bitrix/test` — проверки связи |
| POST | `/api/admin/clear-journal`, `/api/admin/clear-nomenclature` | очистка (с автобэкапом БД) |

## Разбор расходного ордера

Парсер ищет строку заголовков с «Код» **или** «Артикул», «Товар» и «Количество» и распределяет значения
по диапазонам колонок (объединённые ячейки не мешают). Из шапки читаются номер, «Получатель», «Склад» и
**«Распоряжение»** (например, «Заказ клиента № ИБ-15125 от 21 ноября 2026 г.» — идёт в отбивку).

Сопоставление строки с базой ШК (`SkuResolver`) выполняется один раз при открытии ордера:
кандидаты ищутся по коду номенклатуры (форма с «Код») или по артикулу (форма с «Артикул»), затем
«Товар» сравнивается с «Наименование для печати (Характеристика для печати)» после нормализации
(регистр, ё/е, кавычки, любые слеши `\` `\\` `/`, звёздочки в начале, лишние пробелы). Для товаров
без характеристик в скобках может стоять серия — она игнорируется. Строки, которые не удалось
сопоставить, подсвечиваются красным (колонка «ШК») — нужно обновить отчёт по ШК в 1С.

Проверено на формах ИБ-49863 (по «Артикул», 75 из 75 строк) и ИБ-56702 (по «Код», 2 из 2).

## Работа с общей папкой

* «Администрирование» → «Общая папка печатных форм» — сетевой путь, поиск по всем подпапкам.
* На экране «Сборка ФБО» — список `.xlsx` без префиксов «СОБРАН - » и «КИЗ - » (обновляется каждые 15 с,
  есть поиск и переключатель «Показывать собранные»). Файл читается без блокировки — его можно держать открытым в Excel.
* После завершения рядом с исходником сохраняется `КИЗ - <имя>.xlsx` (коды в одну колонку, текстовый формат),
  а исходник переименовывается в `СОБРАН - <имя>.xlsx`.
* Содержимое файла КИЗ — настройка `kiz_format`: `cis` (по умолчанию) — код идентификации `01…21…`
  без крипто-хвоста; `full` — полный код как отсканирован. Немаркируемые товары (EAN) в файл не попадают,
  но учитываются в «Количество единиц».

## Отбивка в Битрикс24

Настройки: URL входящего вебхука (с токеном, хранится зашифрованным AES-GCM, ключ — `data/secret.key`)
и правила вида `БУСТ ЛАЙФ = chat12345` (по одному в строке). Если путь печатной формы содержит папку,
в имени которой есть «БУСТ ЛАЙФ», после сборки методом `im.message.add` отправляется:

```
ФБО
Заказ клиента № ИБ-15125 от 21 ноября 2026 г.
Собран.
Количество единиц: 120
Количество коробов: 4
```

Кнопка «Отправить тестовое сообщение» проверяет связь. Права вебхука: `im`.

## База ШК (отчёт по ШК из 1С)

Колонки: `Штрихкод | Номенклатура.Код | Номенклатура.Наименование | Характеристика.Наименование |
Номенклатура.Наименование для печати | Характеристика.Наименование для печати | Номенклатура.Артикул`
(обязательны первые три). Штрихкод: 8–14 цифр, `(01)GTIN(10)партия`, суффиксы `*`/`**`; GTIN хранится 14-значным.
Загрузка заменяет базу целиком и пересопоставляет открытый ордер. Способы: страница «База ШК» или
автозагрузка из папки/файла (`barcodes_path`, проверка раз в минуту, берётся самый свежий .xlsx).

## Подготовка к объединению с WbPackStation (ФБО/ФБС)

* `Orders.ShipmentType` (`FBO` сейчас) — будущий выбор типа отгрузки при открытии задания.
* Изолированные сервисы без зависимостей от экранов: `ScannerService` (COM), `Gs1Parser`, `TrueApiClient`
  (ЧЗ), `BitrixNotifier`, `SecretProtector` (тот же алгоритм, что в WbPackStation), `OrderFolderService`
  (папки и префиксы), `BarcodeImportParser` + `SkuResolver` (база ШК). Их можно вынести в общую библиотеку.
* План: общий проект `Core` (сканер, ЧЗ, Битрикс, секреты, база ШК) + модули `Fbo` (этот) и `Fbs`
  (WbPackStation), единые настройки и журнал с фильтром по типу отгрузки.

## Ограничения MVP и что делать дальше

- **Токен ЧЗ вводится вручную.** Используется токен для ККТ (разрешительный режим) — он выдаётся один на ИНН
  в личном кабинете ЧЗ (markirovka.crpt.ru → Профиль → «Токен для контрольно-кассовой техники»)
  и передаётся в запросе через заголовок `X-API-KEY`. Старый хост `markirovka.crpt.ru` для этого метода
  больше не работает (HTTP 410). Полноценный True API (для отправки документов оборота, а не просто
  проверки кодов) требует 10-часового JWT-токена с подписью ГОСТ УКЭП
  (`auth/key` + `auth/simpleSignIn`) — в MVP не реализован, т.к. для станции достаточно проверки
  перед продажей.
- **Автообнаружение CDN-площадки.** `https://cdn.crpt.ru` — только точка входа для обнаружения
  (прямой запрос на `codes/check` даёт HTTP 404). При базовом URL `https://cdn.crpt.ru` приложение само
  вызывает `GET /api/v4/true-api/cdn/info`, получает список активных площадок (`cdn01`, `cdn04`...),
  при нескольких — выбирает самую быструю по `cdn/health/check`, и кеширует выбор на 2 часа
  (настройка `cz_resolved_host`). При HTTP 404 от выбранной площадки кеш сбрасывается и обнаружение
  повторяется один раз. Если в настройках указана конкретная площадка (например, `https://cdn01.crpt.ru`) —
  автообнаружение не запускается, запрос идёт напрямую на указанный адрес.
- **Отчёты хранятся в базе** (таблица `OrderReports`) один раз при закрытии ордера, поэтому кнопки
  скачивания в журнале работают повторно (без HTTP 404), даже после перезапуска приложения.
- **Два вида CSV**: простой (только коды маркировки, для вставки в 1С оператором) и подробный
  (сводка расхождений + все коды со статусами, доступен через кнопку «Детали» в журнале). После
  завершения сканирования открывается окно с кодами — можно скопировать в буфер без скачивания файла.
- **Офлайн-тестовый режим ЧЗ** (настройка «Администрирование» → «Офлайн-тест»): позволяет проверять
  работу станции без реального токена и связи с ЧЗ — ответ имитируется случайно (~85% успех,
  15% отказ с разными причинами). Не использовать в продуктивной работе — только для демонстраций/обучения.
- **Нет работы с агрегатами (SSCC/короба)** — сканируются только потребительские КМ.
  При необходимости добавляется запрос состава короба в ЧЗ и автозачёт вложений.
- **Нет возврата результата в 1С.** Логичный шаг: выгрузка кодов в 1С (файл/HTTP-сервис)
  для заполнения документа отгрузки и последующего вывода из оборота.
- **Нет авторизации пользователей** — станция считается доверенной. При необходимости
  добавляется вход по PIN и фиксация оператора в журнале.
- Рекомендуется доработать в 1С кнопку выгрузки строгого CSV/JSON вместо печатной формы —
  это уберёт риск поломки парсера при изменении печатной формы.
- Полезные развития: печать этикетки/акта проверки, контроль сроков годности из ордера,
  дашборд производительности по операторам.

## Опасная зона (администрирование)

На странице «Администрирование» есть раздел «Опасная зона» с двумя отдельными кнопками:
«Очистить журнал сканирования и ордера» (удаляет `Orders`, `OrderLines`, `ScannedItems`,
`OrderReports`, справочник номенклатуры не затрагивается) и «Очистить справочник номенклатуры»
(удаляет базу ШК `Barcodes`, журнал и ордера не затрагиваются). Перед любым удалением обе кнопки автоматически
создают полную копию файла базы данных в папке `data\` с именем вида
`delete-ГГГГ-ММ-ДД_ЧЧ-ММ-СС.db` — на случай ошибочной очистки. Для подтверждения действия нужно
ввести слово **УДАЛИТЬ** — кнопка удаления недоступна, пока слово не введено точно.
